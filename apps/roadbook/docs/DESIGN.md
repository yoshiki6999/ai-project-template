# 随行路书 · 升级设计方案（v0.1）

> 配套：可运行原型（`apps/roadbook/`）、竞品与平台调研全文（`docs/RESEARCH.md`，约 300 条来源，按国际 → 日本 → 中文分组）、产品需求（`SPEC.md`）。

## 0. 结论先看

1. **合并成"一本活的路书"。** 把现在分开的四个视图（卡牌 / 画报 / 导览 / 集景）合并：一张地图打底，按旅行阶段切换「共创 → 路书 → 随行 → 足迹」。同一份数据、同一张地图，不再各画各的。
2. **AI 只负责"出主意"。** 时间对不对、站点在不在、赶不赶得上末班船，由确定性的「路书引擎」把关。AI 输出固定格式的 `roadbook/v1` 数据，引擎校验；不通过就让 AI 自我修正一次。
3. **随行模式是最大的差异化。** 调研显示，Google、高德等地图类产品把"此刻情境"做得很好，但 TripIt、Tripsy 这类路书产品普遍缺位。我们要做好六件事：
   - 下一站倒计时
   - 灵动岛和锁屏上的实时活动
   - 到站自动弹出攻略
   - 晚点后一键重排，守住末班船和演出这类固定时刻
   - 附近检索
   - 带位置的 AI 问答
4. **日本公交是最大的技术风险。** MapKit 的公交路线请求不可靠，Google 在日本的公交覆盖也没能核实。所以 App 内只画步行、驾车线路；公交显示估算时间，加一键跳转（Apple 地图 / Google 地图 / Yahoo! 乘换案内）。中期再接 NAVITIME 或駅すぱあと（Ekispert）的 API。
5. **原型已经能跑。** 网页版可以在 iPhone 上直接打开，在 claude.ai 里会调用真实的 Claude。原生 iOS 版按本文第 7 节的顺序，把各部分换成 MapKit、ActivityKit 等原生能力即可。

## 1. 现状诊断（来自你的 6 张截图）

| 现象 | 问题本质 | 升级做法 |
|---|---|---|
| 四个标签页：卡牌、画报、导览、集景 | 同一份行程被拆成四个产品，切换成本高；行中最需要的"现在该干嘛"没有被放在最前面 | 统一成一张地图加底部面板，模式跟着旅行阶段走 |
| 地图上的路线是直线虚线，6、7 号标记重叠 | 只有起终点坐标，没有交通段几何；标记没有避让 | 每段交通都带 `path`（轨迹点）；同址站点合并（如「7·12」），重叠时自动错开 |
| 画报是 AI 生成的图片，出现"16:53面""约161"这类截断错字 | 图片里的文字不可更新、不可校验 | 手册由数据渲染：文字永远与路书一致，导出时再生成图片或 PDF |
| 编辑卡牌要手填坐标，或按站名定位 | 录入成本高，坐标质量没保证 | AI 生成时直接给坐标，再由地点 ID（MapKit Place ID）校准；校验器拦截缺坐标的站点 |
| 「粘贴攻略生成」是一次性的 | 不能来回改，也看不出改了什么 | 对话式共创：每轮返回方案卡或改动差异（新增 / 调时 / 删除），先预览再生效 |
| 周六 A/B 方案要手动切换 | "停航就切 B"的条件只写在名字里 | `variants[].when` 写明启用条件；行中收到停航信号时一键或自动切换 |
| 时间是死的，没有倒计时 | 行中不知道"还剩多久""会不会赶不上" | 随行模式：倒计时环、晚点识别、动态重排、末班提醒 |
| 集景要手动打卡，否则一直是空的 | 打卡靠人记 | 地理围栏到站自动打卡，轨迹自动记录 |

## 3. 设计原则

1. **地图是画布，面板是工具。** 采用 Apple 地图式三档底部面板：收起（peek）、半屏（half）、全屏（full）。路线永远可见。
2. **AI 出主意，引擎管对错。** 凡是能算出来的（时间、距离、日落、能否赶上），都不交给 AI 猜。
3. **先预览，再生效。** AI 改路书、晚点重排都先给出差异，确认后才写入。
4. **固定的不动，柔性的让路。** 渡轮、演出、预约设为 `fixed`；景点停留可以压缩；`optional` 的点可以取消。
5. **能跳转就不重造。** 公交导航跳转 Apple 地图、Google 地图或 Yahoo! 乘换案内，我们只做"什么时候该出发"。
6. **示例数据明确标注。** 所有示例都标"示例"，正式版接实时数据源。

## 5. 核心机制

### 5.1 对话 → 定稿（AI 协议）

每轮对话，AI 只返回一个 JSON（服务器端用结构化输出 `output_config.format` 强制格式）：

```json
{ "reply": "中文回复 ≤120 字",
  "proposals": [{ "id": "A", "title": "方案 A · 上友岛", "summary": "…", "highlights": ["…"],
                  "durationText": "07:55–18:00", "costText": "交通约 4,410 円", "walkKm": 6.5, "risk": "末班船 16:30" }],
  "roadbook": { "...完整 roadbook/v1，或 null..." },
  "quickReplies": ["两个都要，停航时自动切换", "定稿"] }
```

- 提示词规则写在 `public/core.js` 的 `PLANNER_RULES`。服务器 Claude 和 claude.ai 页面内的 Claude 共用这一份。
- 不确定的店铺不编造，写成类别（如"加太港周边海鲜食堂"），并在 `tips` 里注明需要现场确认。
- AI 返回的路书不带轨迹点。引擎会把未改动交通段的 `path` 补回去（`mergeAIRoadbook`），同时算出改动差异（`diff`），在聊天里高亮。

### 5.2 `roadbook/v1` 数据格式（摘要）

```
Roadbook { schema, title, subtitle, tz, status: draft|final, days[], pois[] }
Day      { id, date: YYYY-MM-DD, label, variants[] }
Variant  { id, name, when(启用条件), stops[] }
Stop     { id, name, nameLocal(日文原名), kind, lat, lng, arrive, depart,
           fixed, optional, minStay, lastDeparture, hours{open,close},
           legIn{ mode: rail|walk|ferry|bus|shuttle|taxi|car, summary, minutes, fare, path[[lat,lng]] },
           tips[], mustBuy, photo, booking, tags[] }
```

时间支持日本时刻表的跨日写法：24:00–29:59 表示次日凌晨。

### 5.3 校验器（`validate`）

| 代码 | 级别 | 含义 |
|---|---|---|
| COORD | 错误 | 缺坐标，地图和导航无法使用 |
| TIME_ORDER / LEG_TOO_SHORT | 错误 | 到达早于上一站出发 / 留给交通的时间不够 |
| STAY_NEGATIVE / TIME_FORMAT | 错误 | 出发早于到达 / 时间格式错误 |
| LAST_DEPARTURE | 错误 | 计划离开时间晚于末班 |
| HOURS | 提醒 | 到达时还没开门，或停留到关门之后 |
| SUNSET | 提醒 | 看日落的站点到得太晚（按天文算法算出当地日落时间） |
| LONG_WALK / LEG_MISSING / VARIANT_WHEN | 提醒 | 步行过远 / 缺交通信息 / 备选方案没写启用条件 |

正式版再加三项：地点 ID 落地（已核实 / 未核实），节假日和定休日，公交 API 返回的真实班次。

### 5.4 动态重排（`replan`）

输入是"我比计划晚了 X 分钟"，规则如下：
1. 后续站点顺延。
2. 遇到 `fixed`（渡轮、演出）或 `lastDeparture`（末班），从约束点往前**压缩停留**，不低于 `minStay`。
3. 还不够就**取消 `optional` 站点**。
4. 还不够就**报冲突**，并给出"改走备选方案"。
5. 人在码头、但开船时间已过 → 直接判定"已错过"。

在示例路书上的实测结果（周六 A，13:30 时在岛上）：

| 晚点 | 结果 |
|---|---|
| 30 分 | 灯台停留缩短 10 分，赶上 16:30 末班船 |
| 60 分 | 炮台缩 25 分 + 灯台缩 15 分 |
| 90 分 | 取消灯台 |
| 150 分 | 报冲突：赶不上末班船 |

### 5.5 实时状态（`liveStatus`）

输入是当前时间，加上可选的真实 GPS，输出：
- 现在在哪一站，或在哪一段交通上
- 下一站，以及离出发还有几分钟
- 预计到达时间，比计划晚多少
- 剩余距离

GPS 在某站 150 m 以内就判定"在站"；否则吸附到最近的交通段，按交通方式的速度估算到达时间。

## 6. iPhone 能力映射（原型 → 原生）

| 功能 | 原型里（网页） | 原生 iOS 用什么 | 备注（调研结论） |
|---|---|---|---|
| 地图与路线 | 自绘矢量底图（GSHHG 海岸线）+ 交通段轨迹 | MapKit for SwiftUI：`Map`、`MapPolyline`、`Annotation` | 步行、驾车用 `MKDirections`；公交只做估算 + 跳转 |
| 地点详情 | 自建详情浮层 | `mapItemDetailSheet`、`LookAroundPreview` | 地点 ID（`MKMapItem.identifier`）用于长期保存 |
| 附近检索 | 内置示例 POI | `MKLocalPointsOfInterestRequest` / `MKLocalSearch` | 可选 Google Places (New) 补充评价，注意 Google 的数据使用条款 |
| 灵动岛 / 锁屏 | 顶部黑色"实时活动预览" | ActivityKit 实时活动 | 单次最长 8 小时，按上午 / 下午 / 晚上分段；iOS 26 可定时启动；会自动出现在 Apple Watch 和 CarPlay 上 |
| 出发提醒 | 倒计时环 | AlarmKit（iOS 26） | "该出发了""末班船倒计时"，静音模式下也会响 |
| 到站自动打卡 | 150 m 判定 + 演示时钟 | CoreLocation `CLMonitor` | 最多 20 个条件：只监控"接下来 N 站" |
| 语音输入 | Web Speech API → Claude 听写 → 提示用键盘听写 | SpeechAnalyzer（iOS 26，端侧） | 中日文支持以官方列表为准 |
| AI 规划 | 页面内 Claude（sample）/ 服务器 Claude API / 演示 AI | 服务器 Claude API（主）；Foundation Models 端侧模型（小任务） | 端侧只有 4096 token，适合抽取和改写；长规划走云端 |
| Siri / 快捷指令 | — | App Intents："下一站是哪""还要多久" | iOS 27 的 Siri AI 支持日语，简体中文暂不可用 |
| 拍照识别 | — | 视觉智能（Visual Intelligence）+ `IntentValueQuery` | 对着店招拍照 → 匹配路书站点 |
| 天气触发备选 | 提示"正式版接 WeatherKit" | WeatherKit | 风速、浪高 → 停航风险 → 推送并建议切 B |
| 交通卡余额 | — | Core NFC（FeliCa） | 读取 ICOCA、Suica 的余额和乘车记录，生成花销 |
| 相册归档 | 足迹页说明 | PhotoKit（按时间、地点归到站点） | 生成旅途长卷或回顾短片 |
| 离线 | localStorage 保存路书 | SwiftData 本地优先 + 提示在 Apple 地图下载离线区域 | 第三方 MapKit 有没有离线下载 API：未核实 |
| 分享 / 手册 | 复制文字版（发 LINE） | 由数据渲染 PDF / 图片 + 共享链接 | 对应日本的旅行手册文化 |

## 7. 原生版实施顺序（按依赖排列，不估工期）

1. **数据层：** 把 `roadbook/v1` 移植成 Swift `Codable` 模型，`validate`、`replan`、`liveStatus` 照搬（规则见 `public/core.js`，测试用例见 `tests/verify.mjs`）。
2. **AI 服务端：** 部署本仓库的 `server.mjs`（Railway 或 Vercel），先跑通 `/api/roadbook/chat`。iOS 端改用"Sign in with Apple + 短期令牌"，代替访问码。
3. **地图：** 用 MapKit 渲染路书，同址站点合并；地点 ID 校准坐标。
4. **共创页：** 聊天、方案卡、改动差异、定稿。
5. **随行页：** 倒计时、`CLMonitor` 到站、晚点重排。
6. **实时活动 + AlarmKit。**
7. **App Intents / Siri 和视觉智能。**
8. **足迹页：** 轨迹 + PhotoKit。
9. **手册导出和多人协作。**
10. **日本公交 API：** NAVITIME 或駅すぱあと，替换估算时间。
11. **灵感导入：** 截图、链接、聊天记录、预订邮件。

## 10. 风险与待决

1. **日本公交数据：** 先跳转外部 App；是否付费接 API，等访谈完真实用户再决定。
2. **目标市场：** 原型界面用中文（与你现有 App 一致）。如果面向日本用户，需要日语化，并强化"旅行手册"导出与多人协作。
3. **AI 准确性：** 坚持"引擎把关 + 示例标注 + 可追溯来源"；坐标最终以地点 ID 校准为准。
4. **实时活动 8 小时上限：** 一天的行程需要分段续开，或用推送更新（注意推送预算）。

## 11. v0.2 升级：对照《AI路书App方案：从串本·白浜一日游的反复修改出发》

| 方案里的要求 | 已实现 | 还没做 |
|---|---|---|
| AI 只把一句话变成"修改操作"，不重写整份路书 | `ops`：insert / remove / replace / update，由 `core.applyOps` 落地；服务器结构化输出已加入 ops，提交前先校验 | — |
| 修改前后对照，确认后才存为新版本，随时可撤销 | 修改预览卡（新增绿、删除红、改时间黄，写明费用变化），地图同时画新路线和旧方案虚影，顶部有"采用/放弃"条；版本只追加，可撤销或回到任意一版 | 版本存在本机，没有接 Supabase |
| 每个时刻带来源，三色核实状态 | 站点与交通段的 `verify`（已核实 / 单一来源 / 未核实 / 冲突），时间轴色点、详情页列出来源；AI 新写的时刻默认未核实 | 没有接交通数据接口做自动核实 |
| 已购票是硬约束 | 票夹，已购票覆盖的路段显示锁；动到不可改签的票、或出现没有特急券的路段，预览里报警 | 截图或邮件导入票 |
| 落后计划时重排 | 按实际到达时间重排，守住固定班次（示例 2："实际 14:07 到白浜"） | — |
| 现场模式"下一步"卡片 + 日语问句 | 大字下一步，日语问句可朗读，一键用 Apple 地图或 Google 地图导航（按步行、公交、驾车自动选方式） | 现场拍照纠错 |
| 方案对比、顺路搜索、离线、同行人共享 | — | 第二、三阶段 |
